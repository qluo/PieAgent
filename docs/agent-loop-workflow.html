Pie Agent Loop Workflow

This sequence begins after the voice application has produced a user question. It shows a full turn, including the optional tool-call loop and the final spoken reply. Durable memory and saved sessions remain outside the core; the application can supply relevant AgentNote entries for this turn.

Sequence Diagram

Version-one behavior: tools execute sequentially. generate(..., streaming=True) emits ModelEvent values; the core forwards them through the turn iterator while collecting the final reply.

Message Types

AgentMessage — core working record

  • user, assistant, and tool_result record the conversation.
  • agent_note carries temporary application context, such as a retrieved preference or repository note.
  • All entries live in AgentConversation.messages.

ModelMessage — LLM-visible input

  • system, user, assistant, and tool_result are provider-neutral.
  • An assistant message may contain a requested ToolCall.
  • convert_to_model_messages() performs the explicit conversion and can omit an internal agent_note.

Core Lifecycle Events

Event pairs

  • agent_started → agent_finished wraps the agent run loop.
  • turn_started → turn_finished wraps one user request.
  • tool_started → tool_finished wraps each requested tool call.

Results and errors live in messages

  • tool_finished carries an AgentToolResult; an error result is also stored as a tool_result message.
  • A handled model failure becomes an assistant error message, then the core emits turn_finished.
  • Streaming remains a separate ModelEvent stream from pie_ai.

Responsibilities During The Turn

pie_ai

  • ModelMessage and ToolSchema are the only model-facing inputs.
  • ModelClient.generate() is provider-neutral.
  • A provider implementation converts the neutral request to its network API.
  • It never executes a tool or changes agent state.

pie_agent_core

  • Agent owns the sequence and repeats model calls after tools.
  • AgentConversation retains this conversation’s AgentMessage entries.
  • transform_context() selects the in-session context; convert_to_model_messages() creates model-visible input. Applications can replace either stage independently.
  • AgentTool is the neutral executable contract and returns AgentToolResult.
  • It has no voice confirmation, coding permissions, or other application policy.

pie_voice_agent

  • VoiceTool implements or wraps AgentTool.
  • It owns spoken status and any confirmation conversation.
  • It can return a declined AgentToolResult without running the underlying capability.
  • A future coding agent can use its own CodingTool wrapper for workspace or sandbox rules.

Memory Boundary

Inside pie_agent_core

  • AgentConversation.messages is the working record of the active conversation.
  • AgentNote is temporary application context carried in that record.
  • Context decides which entries become ModelMessage values.

Outside pie_agent_core

  • The voice app owns session save/restore and any local memory store.
  • It retrieves relevant facts, preferences, or notes and supplies them as AgentNote entries.
  • A coding app can use the same approach for repository context; a shared pie_memory package can wait until it is genuinely needed.

Error handling: a provider error becomes an assistant error message. A tool error or a declined confirmation becomes an error AgentToolResult and a tool_result message, so the model can decide whether to recover, explain the result, or try another tool. Lifecycle events still end with their matching *_finished event.
