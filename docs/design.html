Pie Agent Design

Pie Agent is organized into three one-directional layers. Each layer adds capabilities while remaining removable: the LLM layer works alone, the core builds generic agents, and the voice layer creates the Raspberry Pi experience.

Architecture

pie_voice_agent

Optional application layer for people and devices.

  • Wake word or keyboard input
  • Speech-to-text and text-to-speech
  • Face renderer and spoken status
  • Mac and Raspberry Pi profiles
→

pie_agent_core

Reusable stateful agent runtime.

  • Agent state and conversation history
  • Context transformation and message conversion
  • Neutral tool execution and results
  • Agent lifecycle events
→

pie_ai

Atomic, provider-neutral LLM building blocks.

  • Messages, tool schemas, and model events
  • ModelClient.generate(..., streaming=False)
  • Ollama implementation
  • Future model providers

Dependency rule: dependencies point only to the right. pie_ai never imports agent state, executable tools, memory, face rendering, audio, or Raspberry Pi code. pie_agent_core never imports voice UI, hardware adapters, session storage, or durable-memory implementations.

Layer Validation

1. pie_ai alone

Can send messages to a model and receive a complete response, or streaming updates, tool-call requests, and provider errors when requested.

Use case: a small standalone Ollama SDK.

2. pie_ai + pie_agent_core

Can run a generic tool-using agent without hardware, speech, or a face.

Use case: CLI, web, chat, or future coding agent.

3. All three layers

Runs the complete voice assistant with wake word, transcription, speech, and face feedback.

Use case: Raspberry Pi or Mac voice agent.

Tool Evolution

A model receives a declarative tool schema. The agent core turns it into a safe executable capability. The voice app adds only presentation details.

pie_ai
ToolSchema
  name: str
  description: str
  parameters: JsonSchema

pie_agent_core
AgentTool extends ToolSchema
  execute(arguments) -> AgentToolResult
  # sequential execution in version one

pie_voice_agent
RememberFactTool extends AgentTool
  executes Markdown memory writes

ToolSchema describes what an LLM may request. AgentTool knows how to execute it. The voice application supplies its own concrete tools, such as RememberFactTool.

Model Client API

pie_ai exposes one model operation. The streaming argument controls whether the caller receives one completed response or a sequence of model events.

generate(messages, tools=[], streaming=False)

streaming=False  -> ModelResponse
streaming=True   -> Iterator[ModelEvent]

OllamaClient uses Ollama's chat API, including tool schemas and streamed chunks. The core forwards ModelEvent values when a caller requests streaming while still collecting the completed reply.

Message Preparation Pipeline

The model API and the message pipeline solve different problems. generate() performs one model request. Before that request, the core uses Context to select and convert the current agent history:

AgentConversation.messages
  → Context.transform(messages, conversation)
  → prepared: AgentMessage[]
  → Context.to_model_messages(prepared)
  → ModelMessage[]
  → ModelClient.generate(...)

Context.transform() starts with AgentConversation.messages. It may prune history, compact older messages, and retain useful in-session notes; initially it can return the messages unchanged. The outer application can add an AgentNote from its own memory or repository source before this step. Context.to_model_messages() is a pure boundary that removes UI-only messages and converts application-specific messages into the atomic types defined by pie_ai.

Agent Core Contracts

Agent
  model_client: ModelClient
  tools: list[AgentTool]
  context: Context
  conversation: AgentConversation

AgentConversation
  messages: list[AgentMessage]

Agent.run_turn(user_text, notes=[], streaming=False)
  → Iterator[AgentEvent | ModelEvent]

AgentTool.execute(arguments) → AgentToolResult

The core invokes a neutral AgentTool. Application behavior belongs in the tool implementation: VoiceTool can speak a confirmation, while a future CodingTool can enforce workspace or sandbox rules. The core contains neither policy.

Working Memory, Sessions, and Durable Memory

NeedOwnerExamples
Working memory for this conversation pie_agent_core AgentConversation.messages and temporary AgentNote entries
Save and restore a conversation Optional outer session adapter JSON or SQLite transcript, resume, compaction
Recall durable facts or knowledge Voice/coding application, or a future optional pie_memory User preferences, saved notes, repository retrieval

pie_agent_core owns the first category only. An outer application retrieves durable information, represents any useful result as an AgentNote, and lets Context decide whether it is model-visible. This keeps privacy, storage, and retrieval policy out of the generic runtime.

Message Types

The core keeps a richer agent record than the model sees. Both sets are deliberately small at first.

TypeOwnerVariantsPurpose
ModelMessage pie_ai system, user, assistant, tool_result Exact provider-neutral input supplied to an LLM. An assistant message can include a requested ToolCall.
AgentMessage pie_agent_core user, assistant, tool_result, agent_note Working record in AgentConversation.messages. agent_note carries temporary application context and may be omitted from model input.

Core Lifecycle Events

Events describe lifecycle only. Their payloads carry the relevant message or tool result; errors remain in those messages rather than creating a separate failure-event type.

ScopeEventsMeaning
Agent agent_started, agent_finished The agent run loop has begun or stopped. It can contain many turns.
Turn turn_started, turn_finished A user request is being processed or its final assistant message is ready.
Tool call tool_started, tool_finished A requested tool is running or has produced its AgentToolResult.

A tool error is stored as an error tool_result message and is followed by tool_finished. A handled model error becomes an assistant message and is followed by turn_finished. pie_ai keeps its separate ModelEvent stream for optional streaming output.

One Agent Turn

1. CaptureVoice layer receives wake word and a transcript.
2. PrepareCore transforms agent context, then converts it to model-visible messages.
3. GenerateCore calls pie_ai with model messages and tool schemas.
4. ActCore executes the requested neutral tool and continues the turn with its result. Any voice or coding policy lives in that application’s tool wrapper.
5. PresentVoice layer speaks the reply and updates the face from core events.
